# 새 고민 생성 화면 — 모바일 검증/보정 구현 계획

## 개요
- 이슈: #33 `[feat] 새 고민 생성 모바일 구현`
- 브랜치: `33-feat-새-고민-생성-모바일-구현`
- 피그마 링크: https://www.figma.com/design/Tjb8LmHOOZXQMLSL86LSJC/일상뒤집기-디자인?node-id=0-1 (fileKey `Tjb8LmHOOZXQMLSL86LSJC`, node-id `0:1`은 페이지 루트)
- 관련 화면/노드: "타이머 생성 (새 고민 생성)" 섹션(`265:1660`, x≈-3725, y=6194) 하위의 **모바일 목업 6개 클러스터**(390×812 기준). 상세 좌표는 아래 "피그마 구조 분석" 참고. 라우트는 웹과 동일한 `ROUTES.newWorry`(`/worries/new`, 이미 구현·배포됨)를 그대로 재사용한다 — **이번 이슈는 새 라우트/새 화면이 아니라, 이미 구현된 위저드의 모바일 뷰포트 세부 스펙을 재검증·보정하는 작업**이다.
- 한 줄 요약: `docs/plans/new-worry.md`(이슈 #29)로 상품 정보 입력 → AI 질문 생성 로딩 → 질문 5개 응답 → AI 분석 로딩 → AI 판정 결과 → 타이머 생성 완료의 6단계 위저드가 이미 모바일 우선(mobile-first) 반응형 Tailwind로 구현되어 있다. 이번 이슈는 그 구현을, 이번에 새로 실측한 모바일 전용 피그마 좌표·크기·스타일과 대조해 **이미 정확히 일치하는 부분을 확인하고, 어긋나는 값만 보정**하는 것이 핵심 작업이다.

## 기존 구현 파악 (중요 — 반드시 먼저 확인)

`/worries/new`는 **이미 완성된 라우트**다(`src/pages/NewWorry/index.tsx`, `App.tsx`의 `ProtectedRoute` + `AppLayout` 하위). CLAUDE.md의 반응형 원칙(고정 해상도가 아니라 유동형 구현)에 따라, 이슈 #29 구현 당시부터 모든 스텝 컴포넌트가 **모바일 우선(mobile-first) Tailwind 클래스**로 작성되어 있다 — prefix 없는 기본 클래스가 좁은 화면(모바일) 스타일이고, `lg:`(426px~)/`xl:`(1024px~)가 그 위에 얹히는 구조다. 즉 **"모바일 화면이 아예 없어서 새로 만들어야 하는" 상태가 아니다.**

- `AppLayout`(`src/components/layout/AppLayout.tsx`)이 이미 `Sidebar`(`hidden lg:flex`)/`MobileTopBar`(`lg:hidden`)/`BottomNav`(`lg:hidden`, `fixed bottom-0`)를 전역 렌더링하고 있어 `/worries/new` 페이지도 자동으로 이 셸 안에 들어간다 — 이번 이슈에서 셸(레이아웃) 자체를 손댈 필요는 없다.
- `BottomNav`의 중앙 `NewWorryFab`(`src/components/layout/NewWorryFab.tsx`)이 이미 `ROUTES.newWorry`로 연결되어 있다 — 모바일 진입 동선도 이미 연결 완료.
- 6개 스텝 컴포넌트(`WizardStepper`/`ProductInfoStep`/`AiLoadingScreen`/`QuestionStep`/`VerdictResultStep`/`TimerStartedStep`) 전부 기본(모바일) 클래스를 갖고 있고, 그중 여러 값이 **이번에 재실측한 모바일 피그마 값과 이미 정확히 일치**한다(아래 "컴포넌트별 대조 결과" 참고). 예를 들어 `AiLoadingScreen`의 구름 아이콘 기본 클래스 `h-36.5 w-46`(=146×184px)는 `cloud.svg`의 실제 뷰박스(184×146, 가로세로 배치상 rotate 없이 그대로 매칭)와 정확히 일치하고, `VerdictResultStep`의 아이콘 기본 클래스 `h-22.75 w-22.75`(91px)/`h-25.5 w-25.5`(102px)도 `success.svg`(91×91)/`danger.svg`(102×102) 뷰박스와 정확히 일치한다.
- 다만 `new-worry.md` 자체가 명시했듯, **상품 정보 입력 스텝(`ProductInfoStep`)만 웹(1511px) 실측 스펙에서 파생됐고, 나머지 5개 스텝은 "모바일 목업 기준으로 반응형 적용"이라고만 되어 있어 모바일 쪽 정확한 픽셀 값이 그때 전부 실측되지는 않았다.** 이번 이슈의 실질적 범위는 이 부분 — 특히 `ProductInfoStep`의 모바일 폭(390px) 세부 값(카드/입력창 크기, 여백)을 재검증하는 것이다.

## 피그마 구조 분석 (이번에 재실측)

CLAUDE.md에 설명된 플랫 캔버스 구조이자, `new-worry.md`가 이미 경고한 "배경이 순수 leaf rectangle이라 스크린샷이 빈 화면처럼 보이는" 함정이 이번 모바일 클러스터에도 동일하게 있다. 이번에도 `get_metadata` 좌표 덤프 + 개별 노드 `get_design_context` 방식으로 재조사했다.

1. **모바일 프레임 폭은 390px로 통일**돼 있다(iPhone 14/15 계열 폭). 각 스텝마다 `iOS_topNav`라는 이름의 실제 프레임(390×88)이 존재하는데, 이 프레임은 **내부에 `System/iOS/StatusBar`(47px, 시간/와이파이/배터리/노치)와 빈 스페이서 `Frame 3858`(342×24, 실측 결과 완전히 빈 프레임 — 내용 없음)만 있다.** 즉 88px 전체가 기기 UI 목업용 여백이고 실제 앱 콘텐츠는 전혀 없다 — CLAUDE.md "모바일 디자인 임포트 시 기기 프레임 제외" 원칙에 따라 **`iOS_topNav` 88px 전체를 구현 대상에서 제외**한다(다른 화면들의 상태바 제외 결정과 동일선상).
2. `iOS_topNav` 아래(화면 좌표 기준 y+130 지점)에 3단계 위저드 헤더("상품 정보"/"질문"/"완료" 칩, 각 64×25)가 나타난다 — 이는 실제 앱 콘텐츠이며 이미 `WizardStepper.tsx`로 구현돼 있다.
3. 6개 스텝 헤더 프레임 이름과 좌표(각 프레임 자체는 위 1번처럼 빈 topNav일 뿐이고, 실제 콘텐츠는 같은 x 밴드에 있는 형제 레이어들이다):

   | 스텝 | 헤더 프레임 id | 원점(x, y) |
   |---|---|---|
   | 상품 정보 입력 | (동일 클러스터 내 `265:1690`~`265:1790`대) | x≈-3566, y≈6835 |
   | AI 질문 생성 로딩 | `313:491` | x=2319, y=6835 |
   | 질문 기본화면 | `313:456` | x=3001, y=6835 |
   | 질문 선택시 화면 | `315:574` | x=3423, y=6835 |
   | AI 질문 분석 로딩 | `316:738` | x=4076, y=6835 |
   | 고민 분석 완료 - 긍정 | `316:794` | x=4676, y=6835 |
   | 고민 분석 완료 - 부정 | `325:623` | x=5084, y=6835 |
   | 타이머 생성 완료 | `326:682` | x=5546, y=6835 |
   | (보정 사본, 카피 정확) AI 분석 로딩/판정 긍정·부정 | `334` 클러스터 | x≈3373~7693, y≈9423~10100 |

   `new-worry.md`가 이미 확인한 대로, 판정 결과 카피는 `316:794`/`325:623`(원본, 카피 오류 있음)이 아니라 **`334` 클러스터(보정 사본)를 최종 스펙으로 채택**한다(부정 판정 제목 "충동구매 가능성이 높아요"가 여기서만 올바름).
4. **상품 정보 입력 스텝의 모바일 클러스터**는 이번에 좌표 재조사로 다음을 확정했다(x≈-3566을 콘텐츠 좌측 기준선으로 사용하는 필드들):
   - 이미지 업로드 관련 요소가 y=6891 부근(스텝 헤더 바로 아래)에서 시작.
   - "상품명" 라벨 y=7193, "상품 가격" 라벨 y=7272, "카테고리" 라벨 y=7351 — 필드 순서(상품명→가격→카테고리→URL)는 웹과 동일.
   - **텍스트 입력창(`265:1773`, "상품명" 입력 배경) 실측**: 279×35px, `bg-white border-[#757575] border-[0.5px] rounded-[7px]` — `get_design_context`로 직접 스타일까지 확인. 색상/라운드 값은 웹 실측 스펙(`border-[#757575] rounded-[7px]`)과 완전히 동일하고(모바일에서 색상 토큰이 바뀌지 않는 이 파일의 일관된 패턴), **다른 점은 테두리 두께(0.5px vs 웹 1px, 무시 가능한 차이)와 입력창 높이(35px)** 뿐이다.
   - 동일 클러스터 안에 **거의 동일한 내용의 중복 사본이 최소 5벌 더 존재**한다(x≈-2596, -2555, -1407 등 — 마이페이지/타이머 생성 완료 화면들에서도 반복적으로 나타난 이 파일 특유의 "동일 화면 여러 벌 배치" 패턴). 값 차이는 확인한 범위 내에서 미미했고(라벨/필드 상대 위치 동일), 어느 사본이 "최종"인지 표시하는 별도 라벨(마이페이지의 "기본"/"수정하기 비활성화" 같은 상태 이름)은 발견하지 못했다 — **이 부분은 정밀한 값 차이가 있을 경우 어느 사본이 최종인지 확정할 근거가 없어 "확인 필요"로 남긴다**(아래 참고).
5. **`new-worry.md`가 이미 실측해 확정한 값**(이번에 `334:842`/`334:844`/`334:869` 좌표를 재조회해 그대로 재확인함): `cloud.svg` 184×146, `success.svg` 91×91, `danger.svg` 102×102 — 이 3개 에셋 매칭은 변동 없음.
6. Figma 변수(`get_variable_defs`)는 이번에도 조회하지 않았다(이 파일 전체가 변수 미사용, 하드코딩 hex라는 기존 전례를 따름 — 색상은 개별 노드 `get_design_context`로 직접 확인).

**결론**: 이번 이슈에서 실제로 코드를 바꿔야 할 만큼 명확한 불일치는 **텍스트 입력창 높이 1건**뿐이었고, 이마저도 웹/모바일 높이 체계 일관성과 상충해 사용자 확인이 필요하다. 나머지는 이미 정확히 일치하거나(아이콘 3종), 구조적으로 이미 올바르다(레이아웃/기기 프레임 제외). 즉 이번 이슈의 실질 작업량은 "신규 구현"이 아니라 **위 표의 검증 결과를 바탕으로 한 소규모 미세조정 + 시각적 재확인**이다.

- 반응형 기준: 프로젝트 전역 컨벤션(`src/index.css`의 `--breakpoint-lg: 426px`, `--breakpoint-xl: 1024px`) 그대로. 이 화면은 이미 모바일 우선 구조라 **`426px` 미만이 곧 이번 이슈의 검증 대상 구간**이고, `426px` 이상(사이드바 레이아웃)은 이번 범위 밖(웹은 이슈 #29에서 이미 완료).
  - 폭 390px 피그마 모바일 목업 기준으로 실측했지만, 구현은 고정 390px이 아니라 유동 폭(`max-w-105`=420px 컨테이너 + `mx-auto`, `w-full` 입력창 등)을 그대로 유지한다 — 더 좁은 기기(예: 320px)에서도 콘텐츠가 자연스럽게 줄어들도록 하는 기존 구현 방식을 유지한다.
  - 사이드바처럼 고정 폭을 유지해야 하는 요소는 이 화면에 없다(모바일 뷰에서는 `Sidebar` 자체가 `hidden`).

## 확인 필요 (사용자 승인 시 답변 필요)

1. **텍스트 입력창(상품명/가격/URL) 모바일 높이**: 피그마 모바일 실측값은 35px인데, 현재 구현은 웹과 동일한 44px(`h-11`)를 모바일에도 그대로 쓰고 있다. 두 가지 선택지가 있다 — (A) 모바일 실측값에 맞춰 `h-9`(36px, Tailwind 스케일상 최근접)로 줄인다(피그마 그대로 반영 원칙에 더 충실), (B) 웹/모바일 입력창 높이를 통일해 현재 44px을 유지한다(터치 타깃 접근성 측면에서 36px보다 44px이 더 넉넉하고, 스텝 간 시각적 일관성 유지). **개발 단계에서 AskUserQuestion으로 확인 후 진행할 것을 제안**.
2. **상품 정보 입력 스텝의 모바일 전용 이미지 업로드 카드 크기**: 이번 조사에서 이 클러스터 안에 거의 동일한 내용의 중복 사본이 5벌 이상 발견됐고(마이페이지/다른 화면에서도 나타나는 이 파일 특유의 "동일 화면 여러 벌" 패턴), 사본마다 카드 크기가 미세하게 다를 가능성이 있는데 어느 것이 "최종"인지 구분할 라벨을 찾지 못했다. 현재 구현(`aspect-325/611`, 웹 실측 비율 그대로 재사용)을 모바일에서도 유지할지, 아니면 별도 모바일 비율을 적용할지 확정 짓지 못했다 — **developer가 재확인하거나, reviewer의 스크린샷 대조로 미세조정하는 것을 제안**.
3. **모바일 전용 스크린샷 시각 비교 범위**: 이번 계획은 좌표/치수/색상 위주로 실측했고, `get_screenshot`으로 실제 렌더링 이미지를 픽셀 단위로 겹쳐보는 작업은 하지 않았다(원본 배경이 leaf rectangle이라 스크린샷 자체가 대부분 빈 화면으로 나오는 이 섹션의 알려진 제약, `new-worry.md` 메모 참고). **reviewer 단계에서 실제 브라우저 스크린샷(375px/390px/425px 뷰포트)과 위 표의 실측값을 다시 한번 육안 대조하는 것을 제안**.

## 작업 순서 제안 (developer 서브에이전트용)

1. 이 계획서와 `docs/plans/new-worry.md`를 함께 읽고, 이번 이슈가 "신규 구현"이 아니라 "기존 구현 검증/미세조정"임을 확인한다.
