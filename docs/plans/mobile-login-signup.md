## 현재 상태 파악 / 재사용 판단 (중요)

이번 작업은 **새 화면이 아니라 기존 `/login`, `/signup`, `/signup/complete` 라우트에 반응형 모바일 레이아웃을 추가**하는 작업이다. `docs/plans/home-screen-mobile.md`가 홈 화면에 적용한 패턴(같은 라우트, `AppLayout`에 `MobileTopBar`/`BottomNav`를 반응형으로 얹은 것)과 동일한 성격이다.

- **로직/상태/검증/백엔드 연동은 100% 재사용한다.** 새로 작성하는 로직은 없다.
  - `useAuth()`(`signIn`/`signUp`) — `src/contexts/AuthContext.tsx` 그대로 사용
  - 이메일 정규식, blur 검증, 비밀번호 공백 차단, 5회 실패 잠금(`useCountdown`), "자동 로그인"(로그인 상태 유지) localStorage 처리 — `src/pages/Login/index.tsx`의 기존 핸들러 그대로 사용
  - 닉네임 검증(정규식+금칙어), 비밀번호 강도(`src/utils/passwordValidation.ts`), 비밀번호 확인 일치 여부, `createProfile` 호출, `markSignupJustCompleted` — `src/pages/SignUp/index.tsx`의 기존 핸들러 그대로 사용
  - 목표 금액 검증/포맷(`formatWon`/`parseWon`), `upsertGoal`, `hasJustSignedUpFlag`/`clearSignupJustCompletedFlag` — `src/pages/SignupComplete/index.tsx`의 기존 핸들러 그대로 사용
  - 공용 컴포넌트 `AuthField`(`src/components/auth/AuthField.tsx`), `SubmitButton`(`src/components/auth/SubmitButton.tsx`), `Spinner` 재사용 — 둘 다 이미 사이즈/톤을 props로 조절할 수 있게 설계돼 있어 모바일 실측값도 그대로 수용 가능
  - 아이콘 매핑은 웹에서 이미 확정된 것을 승계: 👁→`Eye`/`EyeOff`, ✓→`Check`, ⓘ→`Info`(lucide-react). 뒤로가기 "←"는 `Notifications` 페이지에서 이미 쓰는 `ChevronLeft` 컨벤션을 재사용한다.
- **새로 작성하는 것은 모바일 전용 JSX 레이아웃(마크업)뿐이다.** 데스크톱과 모바일이 구조 자체가 크게 다르므로(좌측 브랜드 패널 vs 상단 중앙 로고, 헤더+스텝 인디케이터 유무 등), `AppLayout`의 `Sidebar`(데스크톱)/`MobileTopBar`+`BottomNav`(모바일) 분리 패턴과 동일하게 **같은 페이지 컴포넌트 안에서 두 개의 형제 JSX 블록을 반응형 클래스로 토글**하는 방식을 제안한다: 모바일 블록은 `lg:hidden`, 기존 데스크톱 블록은 `hidden lg:flex`(또는 `lg:flex`). 상태/핸들러는 부모 컴포넌트에 한 번만 선언하고 두 블록이 공유한다(로직 중복 없음).
- 반응형 브레이크포인트는 프로젝트 전역 컨벤션(`src/index.css`, `docs/plans/home-screen-mobile.md` 확정)인 `--breakpoint-lg: 426px`, `--breakpoint-xl: 1024px`를 그대로 재사용한다.
  - **< 426px (`lg:` 미적용 구간)**: 이번에 새로 만드는 App 모바일 레이아웃(아래 화면별 상세 참고).
  - **426px ~ 1023px, 1024px~ (`lg:` 이상)**: 기존에 이미 구현된 데스크톱 레이아웃을 그대로 유지한다. 웹 계획(`docs/plans/login-signup.md`)에서 "1024px 미만은 BrandPanel 숨김 + 폼 전체 폭" fallback으로 이미 결정된 부분이라 손대지 않는다(`BrandPanel`은 `xl:flex`만 있고 `lg:` 자체가 없는 상태 그대로 유지 — 즉 426~1023px 구간은 지금처럼 폼만 있는 화면이 계속 나온다). 이 구간을 위한 별도 피그마 디자인은 없으므로 새로 만들지 않는다.
- 이 브레이크포인트 선택 근거: 이슈 배경에서 "홈 화면처럼 반응형 분기 vs 모바일 전용 트리 중 실제 피그마 구조를 보고 판단하라"고 했는데, App 화면이 정확히 390px 폭의 완결된 화면(홈 화면 모바일 프레임과 동일한 성격)으로 그려져 있고 라우트도 이미 `/login`/`/signup`으로 공용이라, **같은 라우트의 반응형 분기(홈 화면과 동일 패턴)**로 판단했다. 별도 라우트(App 전용 트리)로 분리할 이유가 없다(모바일 네이티브 앱이 아니라 반응형 웹이므로).

#### 피그마 원본과 실제 구현 범위의 차이 (중요 — "확인 필요" 1번 참고)
피그마 `182:395`는 **3단계 회원가입 위저드의 2번째 화면**으로 그려져 있다(상단에 뒤로가기+제목 `Header`, 3구간 `StepIndicator`(초록/초록/회색), "2 / 3 단계 · 계정 정보 입력" 라벨 포함). 그러나:
- 1단계(약관 동의) 화면 자체가 이 피그마 파일에 없다(웹 버전도 동일 — `docs/plans/login-signup.md`에서 이미 "약관 동의 UI는 피그마에 없어 생략" 확정).
- 원래 2단계 안에 있던 "이메일 인증코드"(OTP) 스텝은 이번 계획의 "사용자 지정 제외 사항"으로 제거된다.
- 3단계(가입 완료)에 해당하는 화면(`182:475`)은 이번 계획의 화면 3에서 별도로 이미 다룬다(뒤로가기/스텝 인디케이터 없이 독립된 화면으로 그려져 있음).

즉 실제 구현 범위에서는 "3단계 중 2단계"라는 전제 자체가 성립하지 않는다(1단계 화면이 없고, 3단계는 별도 화면). 이 계획은 아래처럼 **Header(뒤로가기+제목)만 유지하고 StepIndicator·"2/3단계" 라벨은 제외**하는 것을 기본안으로 제안한다 — 실제로 존재하지 않는 단계를 가리키는 진행 표시는 오히려 혼란을 주기 때문이다. 다만 이는 피그마에 그려진 실제 UI 요소를 빼는 결정이라 임의로 확정하지 않고 "확인 필요"에 남긴다.
